## Purpose and Ownership

This phase closes the security, privacy, unintended authority, and dependency supply chain risks defined by `SEFAUD-REQ-002` and `SEFAUD-REQ-003`. It starts only after `SEFAUD-PHASE-000` has frozen the execution revision and supplied complete trust boundary, data classification, dependency, artifact, and evidence inventories. It ends only when every inventoried boundary and every current remote dependency alert has an evidence based disposition, every confirmed in scope finding has been repaired with regression proof, and no known authorization bypass, sensitive data leak, backdoor like route, or applicable critical or high exploitable dependency vulnerability remains.

The master plan owns product scope, decisions, platform pins, phase order, and completion authority. This file owns the dependency ordered execution details, finding rules, evidence expectations, remediation loop, verification gates, and downstream handoff for Phase 001 only. It does not authorize new features, a platform migration, publication, production access, or work owned by later phases.

## Finding and Alert Disposition Rules

### Security finding classification

Each suspected issue receives a stable `P001-FIND-###` identifier before remediation. Severity does not decide whether a confirmed in scope issue is fixed. It controls response order, evidence handling, and disclosure sensitivity.

| Severity | Phase 001 meaning | Required response |
|---|---|---|
| Critical | Reliable arbitrary privileged command or code execution, persistent unauthorized authority, broad secret disclosure, destructive path escape, or equivalent compromise with practical preconditions. | Stop unrelated remediation, preserve sanitized evidence, notify the owner privately, repair first, run the full affected adversarial and compatibility set, and do not publish exploit detail. |
| High | Practical authorization bypass, sensitive data disclosure, integrity compromise, cross actor mutation, or exploitable dependency path with material server impact. | Repair before medium and low findings unless a dependency order requires a prerequisite. Rerun every affected boundary and runtime path. |
| Medium | Bounded security or privacy failure, significant defense gap, unsafe failure mode, or denial of service requiring constrained preconditions. | Repair in this phase and add focused regression. It cannot be deferred merely because it is not part of the final critical or high wording. |
| Low | Narrow but real contract violation with limited impact or difficult preconditions. | Repair in this phase and add focused regression. Record why impact is limited without weakening the invariant. |
| Informational | No security contract violation, but a verified observation, hardening note, or later phase evidence need. | Record as an observation, not a confirmed finding. Route genuine later phase work to its existing requirement without using it to hide an open Phase 001 defect. |

Valid dispositions are `confirmed and repaired`, `not reproducible at frozen revision`, `duplicate of`, `inapplicable with proof`, and `blocked`. A `blocked` mandatory row prevents exit. `Accepted risk`, `historical`, `transitive only`, `default branch only`, `test only`, and `not packaged` are not sufficient dispositions without the required technical evidence. A confirmed authorization bypass, sensitive data leak, unintended authority path, or other `SEFAUD-REQ-002` violation is mandatory remediation at every severity.

### Dependency alert disposition

Each remote alert receives a stable `P001-DEP-###` row that preserves the remote alert identifier. The table must include advisory identifier and authoritative source, severity at capture, affected coordinate and range, every candidate dependency path, resolved configurations, whether the component is direct or transitive, packaged class or metadata presence, affected API, static and runtime reachability, exploit preconditions, candidate applicability, chosen compatible remedy, tests, remote state, and invalidation triggers.

An alert may be `inapplicable with proof` only when exact graph and artifact evidence establishes absence, the vulnerable configuration or API is not used, or the advisory does not apply to the pinned candidate. Compile only, test only, tooling, and default branch differences must still be recorded. An applicable finding must be repaired even when transitive. If a critical or high finding is applicable and exploitable but no compatible remedy exists inside `DEC-004`, Phase 001 is blocked and the owner must decide whether to revise the platform contract. No alert may be dismissed remotely as a substitute for candidate evidence.

### Ordering, Failure Handling, and Safe Parallel Work

Task 001 is an absolute gate. Task 002 establishes stable rows and must complete before specialist review. Tasks 003 through 009 may proceed in bounded parallel work only against the same frozen revision and only when they write separate evidence rows. A reviewer who finds a missing Phase 000 surface stops that row and routes it back to Phase 000 rather than silently extending the baseline.

Task 010 is the only remediation convergence point. Shared files such as `KernelServices`, permission services, protocol handlers, storage primitives, `build.gradle`, and generated metadata must have one change owner at a time. Repairs are atomic by finding where practical. If a repair fails verification, restore the last verified phase branch state through a normal corrective commit or remove only the isolated unmerged change. Never use destructive history rewriting or discard unrelated work.

Tasks 011 through 014 use the final repaired revision. A newly found defect returns to Task 010. A dependency or artifact drift returns to Task 009. A missing inventory row returns to Phase 000. A documentation discrepancy returns to Task 013. Any post verification product change invalidates the exact affected evidence and requires the mapped rerun before integration.

## Architecture and Implementation Boundaries

### Authority and execution

The logical server remains authoritative for identity, source classification, permissions, hierarchy, exemption, targets, policy, revisions, confirmation, execution, persistence, and audit. `CommandExecutionService` and the canonical command policy pipeline remain the required gate for executable catalog actions. Aliases, shortcuts, bundles, command profiles, sudo, panels, GUI actions, scheduled work, and approved integrations must resolve to a canonical action and cannot create an alternate permission or source policy.

Permission and feature decisions made during discovery, preview, suggestion, or GUI projection are not mutation authority. Current feature, permission, provider, hierarchy, exemption, source, target, command tree, configuration, session, panel, and record revisions must be checked immediately before a privileged effect. Temporary authority is immutable, narrow, expiring, single use where declared, cleaned in all terminal paths, and incapable of creating a persistent grant or delegating itself.

### Networking and GUI

Client payloads and client caches are untrusted presentation input. Codecs enforce byte, string, list, page, component, image, chunk, and aggregate bounds before large allocation or native decode. Handlers bind player identity to the connection, negotiate supported features, validate session and monotonic sequence, reject replay and stale state, select only server projected identifiers, and schedule server mutation on the logical server thread. An enhanced, absent, fallback, or incompatible client never changes server authorization semantics.

### Configuration, persistence security, and filesystem ownership

Configuration, migration, recovery, import, archive, image, and persistent documents are untrusted even when located under an owned directory. Normalization alone is insufficient. Each boundary validates root containment, every existing parent, entry type, symbolic links, detectable hard links where the contract requires them, file type, size, encoding, structure, schema, semantic bounds, and revision. Publication preserves the last known good state and recovery evidence.

Phase 001 owns privilege, disclosure, path escape, unsafe parser, and evidence destruction risks at persistence boundaries. Phase 002 owns exhaustive durability and cross store integrity. A Phase 001 repair that changes schema or configuration must still supply a versioned migration, source identity and revision binding, complete staged validation, exact recovery copy, rollback, and forward and backward fixture evidence before integration.

Archives must reject traversal, absolute names, duplicate normalized names, links and special entries, excessive nesting, excessive entries, excessive compressed or expanded bytes, and unsupported content before extraction or publication. Images must be structurally bounded and validated before native decode, with encoded bytes, dimensions, pixel count, frames, metadata, and canonical output constrained. Exports use opaque identifiers or safe fixed names and never disclose host filesystem paths.

### Audit, logging, privacy, and evidence

Mandatory security audit remains independent from optional observation and file logging filters. Every privileged attempt has stable action metadata, real and effective actor attribution, source class, result, correlation, and bounded diagnostic context. Audit integrity does not authorize recording sensitive arguments. Redaction happens before filtering, persistence, export, or broad projection. Unknown or malformed roots receive the safer redaction class.

Evidence uses synthetic identities and unique synthetic canary values. Tracked summaries contain hashes, stable IDs, commands, expected and actual classes, and sanitized excerpts only. Raw captures remain in the Phase 000 approved restricted location with bounded retention. If a real credential or personal value is unexpectedly detected, stop inspecting or copying it, quarantine the affected evidence, report only the type and location privately, and let the credential owner perform any required rotation.

### Integrations, reflection, mixins, and access transformers

Optional integrations remain behind runtime presence checks and bounded adapters. Reflection is contained to named optional compatibility surfaces, validates types and return values, catches linkage and reflection failures at the adapter boundary, and cannot grant on failure. Provider caches have explicit revision, refresh, expiry, and outage behavior. Core startup and command fallback remain available when optional integrations are absent.

Every Mixin and access transformer is privileged compatibility surface. The review records target, purpose, logical side, injection or access scope, failure behavior, supported platform, composition risk, test, and packaged presence. Client mixins remain under the client list. Common and dedicated server paths cannot load client classes. A security repair may narrow a hook but cannot broaden platform support or introduce a new Mixin when a current supported API or event can safely express the repair.

### Dependency, license, and provenance

Resolved candidate graphs, not declared coordinates alone, define dependency state. The graph capture covers plugin and buildscript dependencies, main compile and runtime classpaths, fallback runtime classpaths, unit and GameTest classpaths, annotation or tooling configurations if present, generated metadata inputs, and the actual packaged JAR. Configuration names are taken from the live Gradle model rather than assumed. For each component, record coordinate, version, dependency path, repository or origin, a computed artifact checksum, license evidence, optional status, configurations, packaged presence, and advisory disposition.

A dependency remedy prefers the smallest compatible direct version, constraint, exclusion, or upstream selection that removes the applicable vulnerable path without violating `DEC-004`. Optional dependencies remain optional and do not become embedded by accident. A version override is not accepted until clean resolution, compilation, unit tests, GameTests, dedicated server, affected client, optional integration present and absent, and artifact inspection pass.

### Concurrency and performance

Security checks and state consumption must be atomic at their owning boundary or protected by current revision and conditional mutation. Race tests cover permission revocation, provider refresh, session close, upload ownership, archive settle windows, config file replacement, migration, export preview and confirmation, log retention, temporary grant use, and timeout cleanup. Exactly one authorized terminal outcome is permitted where operations race.

No repair may add unbounded scans, allocations, decompression, payload buffering, per tick filesystem access, blocking network work, reflection, or log spam to tick, packet, render, command, audit, or persistence hot paths. Bounds are tested at just below, exact, and just above limits. Repeated invalid input is rate limited or bounded and produces summarized audit evidence rather than one unbounded record per attempt.
