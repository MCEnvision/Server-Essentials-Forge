## Purpose and Ownership

Phase 005 closes the lifecycle integration boundary at one approved candidate. It proves construction, registration, server start, login, reload, revocation, world and dimension transitions, logout, reconnect, shutdown, and the next restart. It also proves that optional integrations, canonical execution channels, configuration revisions, caches, sessions, payloads, durable outcomes, native audit writes, and worker ownership converge on the same logical server result.

The master plan owns product scope, acceptance criteria, interface definitions, budgets, host policy, decisions, and phase topology. This phase owns only detailed execution of SEFAUD-REQ-007. It preserves the Phase 000 inventory as the exhaustive source of lifecycle, transient-owner, provider, payload, worker, native, and evidence rows. A source path, mock, old packet, or successful start is not proof of the required lifecycle outcome.

The canonical runtime is a no GUI disposable dedicated server on node-1 for server-observable work. A residual receipt, rendering, input, or reconnect claim uses the exact silent Linux laptop client and the verified private server endpoint. This is one portable Minecraft Java client contract across Linux, macOS, and Windows. It neither requires foreign client sessions nor permits a client on node-1. EXT-001 and EXT-002 are available in-plan closure work, not unavailable prerequisites.

SEFAUD-IF-004 is an integrated Phase 003 base contract at Phase 005 entry. If its delivered capability, control behavior, or a compatible typed subsystem signal is missing or broken, repair it on the current Phase 005 branch under the frozen interface before the dependent fixture runs. Rerun its producer control proof and every affected fixture proof. Canonical owner identifies the contract and its evidence responsibility, not a historical branch, phase rerun, or cursor rewind. This repair may not alter the schema, category enum, controls, budgets, or existing history.

## Architecture and Implementation Boundaries

The logical server owns authority, lifecycle state, revision publication, provider decisions, domain mutations, durable outcomes, and terminal audit correlation. Clients render and collect input only. A C2S payload is bounded typed intent, never authority, and enters the server through its authoritative validator and declared server thread. S2C state is presentation data, and client caches cannot become a source of authorization.
