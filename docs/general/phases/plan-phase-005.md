## Purpose and Ownership

This phase closes `SEFAUD-REQ-007` by proving and, where a defect is confirmed, repairing the complete backend lifecycle and every supported cross-channel route at the integrated revision produced by Phase 004. Its endpoint is not merely a server that starts. It is a lifecycle whose construction, registration, startup, world and player transitions, runtime revisions, optional providers, command and enhanced-client channels, partial failures, and shutdown all preserve one logical-server authority model, one domain result, and one correlated audit lifecycle.

The canonical owner is the lifecycle integration boundary. Current evidence places that boundary primarily in `src/main/java/com/enviouse/sef/ServerEssentialsForge.java`, `src/main/java/com/enviouse/sef/kernel/KernelServices.java`, `src/main/java/com/enviouse/sef/events/CommandRegistrationHandler.java`, `src/main/java/com/enviouse/sef/events/PlayerEventHandler.java`, `src/main/java/com/enviouse/sef/events/ExternalModLoadingEvent.java`, `src/main/java/com/enviouse/sef/config/ConfigurationEventHandler.java`, `src/main/java/com/enviouse/sef/config/modules/ModuleConfigService.java`, `src/main/java/com/enviouse/sef/gui/protocol`, `src/main/java/com/enviouse/sef/permissions/PermissionRefreshBridge.java`, `src/main/java/com/enviouse/sef/storage/repository/StorageCoordinator.java`, and the stateful domain services invoked from them. Phase 000's authoritative inventory remains the source of truth for the complete set of handlers, revisions, integrations, transient owners, and durable owners. This file does not replace or narrow that inventory.

The master plan owns product scope, `DEC-001` through `DEC-008`, platform compatibility, global requirement ownership, phase topology, and the final Definition of Done. This file owns only the dependency-ordered execution of `SEFAUD-PHASE-005`. It may remediate confirmed integration defects and add the minimum instrumentation or test harness required to prove them. It may not add new features, implement the sixteen intentionally unavailable control families, broaden platform support, publish or deploy a release, or substitute historical evidence for execution at the frozen phase revision.

## Architecture and Implementation Boundaries

### Lifecycle ownership and ordering

`ServerEssentialsForge` remains the NeoForge entry point and top-level lifecycle coordinator. `KernelServices` owns the shared service graph and must not become dependent on client presentation. Event handlers and domain services may respond to lifecycle transitions, but each state mutation must have one canonical owner and one cleanup owner. Duplicate event subscribers, legacy managers, and static runtime helpers are audited as separate owners rather than assumed to be covered by the kernel shutdown.

The required ordering model is:

1. Construction registers mod-bus network and configuration callbacks, registers NeoForge event listeners, starts only bootstrap-safe modular configuration work, and prepares immutable permission, descriptor, catalog, and action metadata.
2. Command registration consumes a prepared and sealed manifest and captures external roots before publishing shortcuts, aliases, or other collision-aware routes. It must not depend on world-scoped storage or an online player.
3. Server startup activates the configured protocol mode, initializes the service graph once, publishes the current module snapshot, opens world or server-scoped storage and profile data, starts mandatory audit before privileged activity, starts optional observation workers, writes runtime manifests, loads enabled legacy managers, and starts optional integrations only after their prerequisites exist.
4. World readiness is explicit. Any owner that needs registries, dimensions, save roots, or world data must wait for the correct server or level lifecycle point. World unload or replacement must not leave a path, entity, level, or worker bound to the previous world.
5. Player login first applies admission or maintenance policy and recovery reconciliation, then establishes authoritative identity and state, executes eligible deferred work, negotiates or binds optional client presentation, publishes projections, and delivers login workflows. A disconnected or denied player must not retain state from a partially completed login.
6. Tick work executes only after its owner is ready, observes feature and module state at the declared revision, uses bounded budgets, performs no unexpected filesystem access on the server thread, and remains safe while zero players or multiple dimensions are present.
7. Reload and module publication validate a complete replacement before publication. After publication, dependent policy, caches, command trees, sessions, panels, projections, and workers refresh or invalidate on the server executor in a deterministic order. Failed candidates leave the previous known-good state active.
8. Provider refresh invalidates provider caches and revisions before it refreshes downstream command trees and presentation. An online actor cannot mutate through the old decision after the provider revision advances.
9. Logout and other player transitions revoke actor and target dependent work before the identity or connection can be reused. Cleanup is idempotent and safe after partial login.
10. Stopping prevents new work, settles or marks workers and durable operations, stops providers and watchers, clears sessions and transient state, and drains persistence according to Phase 002. Stopped callbacks remove any state whose API requires the terminal event. The next startup must not see an owned resource from the prior server unless its persistence contract explicitly reloads it.

Where current event dispatch does not guarantee a required relative order, implementation must encode the prerequisite through an explicit state, coordinator call, event priority justified by NeoForge behavior, or idempotent dependency check. Do not rely on incidental class discovery or registration order without evidence.

### Authority, revisions, and state flow

The logical server remains authoritative. A client request, stored alias, bundle step, sudo command, scheduled job, profile, panel entry, provider response, cached projection, or persistent record is input to current policy, never authority by itself.

Every admitted mutation must bind the revisions it depends on. At minimum, the matrix evaluates:

- Feature and module state, including dependency state and the current published module revision.
- Permission provider revision, exact permission decision, hierarchy, exemption, delegated authority, and temporary lease state.
- Command definition, dispatcher or command-tree, shortcut ownership, alias, bundle, server profile, and policy revisions.
- Configuration revision and every restart-required drift state relevant to the action.
- Actor connection, target identity and connection, target world or dimension, inventory or entity state, and target visibility revision where applicable.
- Enhanced session id, request sequence, negotiated feature mask, session authorization revision, panel id and revision, workflow or draft revision, selected entry revision, confirmation expiry, and projection revision.
- Domain record, repository, persistence, operation, journal, receipt, escrow, and queue revisions.

Invalidation occurs before the final permission and policy check and again before mutation if asynchronous or deferred work intervenes. A stale result returns a bounded conflict or revoked-state response and one correlated rejection audit. It never silently refreshes and executes an action the actor did not explicitly resubmit.

### Cross-channel convergence and correlation

The canonical action id is the join key across commands, shortcuts, enhanced GUI, fallback command workflows, aliases, bundles, sudo, panels, scheduled work, server profiles, and approved integrations. Convenience channels may adapt typed input and presentation but may not create a different permission root, bypass current source restrictions, reset cost or cooldown, weaken confirmation, select a hidden target, or omit mandatory audit.

Correlation must cover the top-level request and every nested or deferred step without exposing restricted arguments. The result must distinguish real actor, effective actor, source type, origin, canonical action, target ids, definition and policy revisions, provider context, nested job or step identifiers, result, reason, duration, and redaction class. A partial failure may produce multiple component events under one correlation id, but it must not produce two successful top-level lifecycle records for one effect.

### Networking and client compatibility

`SefNetwork` remains an optional versioned transport. Matching clients may negotiate the supported feature intersection. Missing clients, missing channels, major incompatibility, unsupported minor features, disabled enhanced GUI, exhausted negotiation capacity, stale sessions, replay, and out-of-order sequences must leave command fallback available and must not kick a player solely for lacking enhanced capability.

Client-to-server payload handlers decode bounded typed payloads and enqueue work. The server then revalidates the current player, session, sequence, feature, permission, policy, panel, target, record, and persistence state. Client screens, HUDs, caches, projections, and native resources are presentation only. They clear on logout, disconnect, reconnect, server switch, mode disablement, permission loss, module disablement, and shutdown according to their owner contract.

No protocol version bump is assumed. If a confirmed fix changes a wire shape, the implementation must preserve compatible decoding or use the existing protocol versioning mechanism, add matching and incompatible fixtures, and update compatibility documentation. Broad protocol expansion is excluded.

### Providers and optional integrations

Every optional integration is runtime guarded and isolated from unconditional common classloading. Provider installation and removal must be atomic from the consumer's view. Listener handles, caches, quota providers, group resolvers, nickname owners, inventory adapters, and diagnostics must be replaced or cleared together. Failure cannot preserve a partially installed adapter.

A provider may grant only through its declared current decision. Timeout, exception, linkage error, malformed result, stale cache, removal, or shutdown uses the documented internal fallback or denies the provider-owned capability. Fallback must be finite and bounded where the contract requires it. Restoring a provider advances revisions and requires a fresh decision; it must not revive an old confirmation, session, grant, or cached command tree.

### Persistence, partial failure, and recovery

Phase 002 remains authoritative for file, schema, atomicity, worker, journal, receipt, migration, and recovery contracts. Phase 005 owns their ordering with game and integration effects. Each cross-boundary operation declares its commit point and whether game effect, cost, cooldown, escrow, persistence, audit, queue, or adapter work occurs before or after it.

Nonidempotent work requires a durable operation id, journal, receipt, compensation, or outcome-unknown resolution sufficient to prevent duplicate retry. A mandatory audit failure cannot be hidden behind successful optional observation. An optional file-log failure must not rewrite the mandatory domain result, but diagnostics must show observation degradation. A persistence failure after a reversible game effect triggers compensation. An irreversible effect with ambiguous persistence enters explicit recovery or outcome-unknown state and blocks blind retry.

### Concurrency, threading, and performance

Server state is read or mutated on the logical server thread unless an owner captures an immutable snapshot there and publishes it through a bounded worker. Network handlers use their provided scheduling mechanism. Module watcher work may parse outside the server thread, but publication and downstream Minecraft mutations use the configured server executor. Client texture and screen work stays on the render or client thread. Shutdown workers may flush immutable snapshots but may not traverse mutable levels, entities, player lists, or inventories.

Locks and synchronized owners must have a documented order where they interact. Never call an optional provider, filesystem, blocking future, or network operation while holding a broad game-state monitor. Queue, scan, projection, reconnect, and refresh work must have explicit capacity and per-pass budgets. Failure and diagnostics must be rate limited enough to avoid tick or log denial of service.

### Compatibility and security constraints

Preserve `DEC-004`, existing public ids, persistent schemas, and supported optional-integration contracts. Any schema or protocol repair uses the smallest existing versioning mechanism and the migration or fallback rules in the master plan. Unsupported newer state fails explicitly.

Every lifecycle callback and channel is a trust boundary. Validate source, actor, effective actor, session, target, provider, revision, path, size, expiry, thread, and current server identity. Do not place tokens, private messages, network addresses, hidden identities, raw provider metadata, sensitive command arguments, host paths, or unbounded exception text into diagnostics or evidence. Tests use synthetic identities and disposable data only.
