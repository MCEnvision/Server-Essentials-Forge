## Purpose and Ownership

This phase delivers the complete `SEFAUD-REQ-005` closure for graphical and textual operator UI after Phase 003 has stabilized command semantics, permissions, effects, feedback meaning, audit identities, and intentionally unavailable states. It audits, remediates, and verifies every in-scope enhanced screen, container screen, HUD, pause entry, workflow, panel, picker, Fancy Tags presentation, and administrator command feedback surface. The measurable outcome is a responsive, accessible, state-clear, privacy-safe, server-authoritative operator experience with semantic equivalence between enhanced and command fallback clients and no known blocking or materially misleading UI defect.

The master plan owns global scope, decisions, compatibility boundaries, phase order, the completion defect boundary, and the plan-wide Definition of Done. This file owns only the detailed execution of `SEFAUD-PHASE-004`. It does not authorize product expansion, platform changes, publication, production mutation, or work assigned to later phases.

## Scope Boundaries

### Included Scope

- `SEFAUD-REQ-005`: inventory, polish, remediate, and verify every in-scope graphical, HUD, workflow, fallback, and administrator-feedback UI for layout, responsiveness, accessibility, state clarity, safe projection, and server-side authorization.
- Every current direct `SefScreen` subclass: `FancyTagStudioScreen`, `SefControlEditorScreen`, `SefItemPickerScreen`, `SefPanelScreen`, `SefPlayerPickerScreen`, `SefSuggestionPickerScreen`, and `SefWorkflowScreen`.
- `SefInvSeeScreen`, including enhanced target presentation over the same server-authoritative container used by fallback clients.
- The dashboard and every panel, category, detail, search, pagination, typed form, preview, confirmation-pending state, progress, success, failure, empty, loading, and unavailable view emitted through `SefPanelScreen`, `SefControlEditorScreen`, and `SefWorkflowScreen`.
- Player, multi-player, server-authoritative suggestion, registry item, and other typed picker paths, including vanish-safe and permission-filtered records, modded registry content, native item icons, and one bounded native tooltip at a time.
- Fancy Tags gallery, local project, management, editor, upload and transfer state, local provenance, chat glyph, nameplate, HUD, missing texture, cache, and error presentation that exists in the current product.
- `SefClientEvents` pause-menu button, HUD tiles, progress surfaces, local overlay, identity and disguise-facing presentation hooks, screen invalidation routing, disconnect cleanup, and coexistence with vanilla and supported overlay regions.
- Administrator command feedback for every Phase 003 executable administrator action and every intentionally unavailable negative row, including headers, labels, values, paging, success, denial, validation, partial completion, recovery, degraded, unavailable, and failure states.
- Enhanced and fallback semantic equivalence: the same domain result, canonical action id, permission and policy outcome, audit identity, and safe operator meaning, while presentation may differ by negotiated capability.
- Remediation of every confirmed in-scope blocking or materially misleading UI defect and regression proof at its real boundary.
- Phase-owned tests, documentation updates, sanitized screenshots and recordings, phase evidence, and repository phase integration.

### Explicit Exclusions

- `FUT-001` and `NG-001`: do not implement the sixteen intentionally unavailable control-family runtimes. Their UI must remain clearly unavailable, unreachable, permission-safe, side-effect-free, and negatively tested.
- `FUT-002`: do not add unrelated commands, screens, HUDs, controls, integrations, or gameplay features.
- `FUT-003`: do not perform broad UI framework replacement, architecture modernization, or class decomposition beyond confirmed-defect remediation or mandatory evidence enablement.
- `NG-002`: do not change Minecraft, NeoForge, mappings, Java, Gradle, loader, or protocol boundaries.
- `NG-003` and `DEC-005`: do not publish, deploy, mutate production systems, use production worlds, or use real credentials or personal data. All destructive or privacy-sensitive workflows use disposable synthetic fixtures.
- Phase 005 backend lifecycle closure, Phase 006 full clean-checkout release matrix, and Phase 007 final documentation and endpoint audit remain owned by their phases. Phase 004 must still run the focused lifecycle, build, server, client, fallback, and mixed-client checks needed to prove its own changes.
- New custom fonts, textures, shaders, browser panels, resource-pack requirements, or artwork outside the existing bounded Fancy Tags content model are not authorized.

## Architecture and Implementation Boundaries

### Ownership and dependency direction

- The logical server owns identity, visibility, permissions, feature state, target selection, suggestions, page contents, action availability, preview, confirmation, revisions, and mutation. Client screens own only presentation, navigation, safe filtering of already-authorized rows, unsent bounded drafts, and local preferences.
- `UniversalGuiCatalog`, `GuiWorkflowCompiler`, and server domain owners describe semantic actions and typed fields. They must not provide executable callbacks, raw command strings, arbitrary client classes, pixel coordinates, or trusted client-supplied authority.
- `SefGuiServer`, `GuiWorkflowService`, `SefSessionManager`, `SessionRequestGuard`, `PanelActionValidator`, and typed payload codecs form the server trust boundary. Every privileged request is bounded, session-bound, sequenced, capability-gated, revision-bound, permission-checked, and revalidated before mutation.
- `ClientProtocolState` is a presentation cache. It cannot become durable authority. Disconnect, server switch, incompatible negotiation, module disablement, permission loss, and relevant revisions clear or invalidate dependent presentation.
- `SefScreen`, `SefScreenBackground`, and `SefVanillaTheme` own shared visual behavior. Screen-specific code may specialize content, but must not silently diverge from background, focus, contrast, tooltip, narration, resize, and state semantics.
- `SefInvSeeScreen` remains a presentation of the same authoritative menu and click validation used by fallback clients. Enhanced layout cannot introduce an alternate inventory mutation protocol.
- Fancy Tags local projects and local preview remain client-owned and visibly local. Server publication, assignment, permissions, revisions, canonical image facts, visibility, audit actor, and object authorization remain server-owned. Local artwork must never appear server-approved without explicit provenance.
- Administrator feedback must preserve the Phase 003 action and audit contract. Presentation remediation may restructure components, labels, and pagination, but cannot change authorization, effect, route, action id, redaction, or source semantics without reopening the owning earlier phase.

### Visual design system

- Use vanilla-native widgets, fonts, item rendering, tooltips, focus treatment, and restrained colors. Do not require custom textures, fonts, shaders, browser surfaces, or a resource pack. Fancy Tags artwork is bounded user content, never general UI chrome.
- Each surface declares a title, purpose, primary status, content region, primary action, secondary navigation, destructive action treatment, and location for validation or result announcements. Meaning cannot depend on color alone.
- Labels and values are distinct. Truncation may protect bounded layout only when the complete value is available through an accessible tooltip, detail view, wrapping, or paging and disclosure is authorized.
- Destructive actions state object, scope, consequence, and irreversibility or recovery. Confirmation must describe the exact server-bound preview and cannot be reused after a relevant change.
- Loading, empty, no-match, unavailable, denied, validation, stale, degraded, error, partial success, success, and closed states are not interchangeable. Each state provides the safest useful next action.
- Unavailable controls remain discoverably unavailable only where the current permission-filtered contract allows discovery. They cannot look ready, preview successfully, or expose a mutation affordance.

### Layout, input, and accessibility

- Layout must adapt to actual GUI-space dimensions rather than assume that a centered fixed panel fits. Required content must remain reachable at scales 1 through 4, 854 by 480, 1280 by 720, narrow and wide representative ratios, and during live resize.
- When all content cannot fit simultaneously, use bounded scrolling, paging, wrapping, or a compact state-specific layout with visible position and navigation. Do not clip required controls, hide them below the window, overlap them, or rely on mouse wheel access without keyboard equivalence.
- Define deterministic focus order from title or first actionable control through content, pagination, primary action, and back or close. Rebuild and resize preserve the nearest safe logical focus without restoring stale authority.
- Escape and back return to the correct parent without double-sending close requests, losing permitted unsent local work, or retaining server-side session state. Disconnect and invalidation close to a safe vanilla or parent surface.
- Narration names the screen, current state, focused control, required field, validation error, destructive consequence, progress update, and final result without narrating hidden data. Repeated rapid updates are coalesced so narration remains usable.
- Tooltips belong to one hovered or focused control, stay within the viewport, expose full authorized content, and never cover the action being described without a keyboard-accessible equivalent.
- Long localized strings, long player or registry names, and long authorized values must not break layout. Use at least one deterministic long-string locale fixture, not ad hoc manual text edits.

### State, privacy, compatibility, and invalidation

- Unauthorized entries, controls, targets, identities, records, and fields are omitted from server projection. Disabling a leaked private row is a failure.
- Unknown and unauthorized players use the same safe unavailable meaning where distinction would disclose vanish, membership, or private state. Search and counts must not leak filtered records.
- Suggestions and item or player pages are server-authoritative where permissions or privacy apply. Client search may narrow an authorized page but cannot infer or request arbitrary hidden records.
- Permission, hierarchy, exemption, feature, module, policy, command definition, target, record, inventory, provider, configuration, and session revisions invalidate only the dependent state, but always before a privileged mutation.
- Enhanced, fallback, GUI-off, and incompatible clients preserve command access and equivalent domain semantics. No enhanced payload is sent to a connection that did not negotiate the feature.
- Wire shapes, action ids, serialized fields, permission ids, translation keys, and routes remain stable unless the smallest compatible or versioned repair is necessary. Unsupported newer state fails explicitly.

### Concurrency, threading, and performance

- Client widget construction and render-state mutation run on the client thread. Server mutations run on the logical server thread. Background image, cache, search, or persistence work may publish only immutable validated results to the owning thread.
- Render, tick, narration, and input paths perform no filesystem or network access, blocking waits, unbounded registry scans, or repeated full-domain recomputation. Item and player lists, Fancy Tags textures, HUD deltas, and search results remain bounded and paginated or indexed.
- Rapid search replacement, progress updates, permission refresh, config reload, mass invalidation, HUD delta bursts, and texture availability changes cannot reorder stale state over a newer revision.
- Screen close, disconnect, server switch, and module disablement release sessions, transfers, textures, overlays, drafts according to ownership. Local unsaved Fancy Tags work may survive only under the documented local recovery contract.
- Evidence capture must not materially change timing or hide performance failures. Record capture tooling and repeat performance-sensitive rows without capture overhead.
