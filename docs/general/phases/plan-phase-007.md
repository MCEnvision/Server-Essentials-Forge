## Purpose and Ownership

This final phase reconciles every current documentation claim and every sanitized evidence reference with one final integrated SEF 2 candidate, proves plan-wide traceability and the complete Definition of Done, and records release readiness without publishing or deploying anything. It owns `SEFAUD-REQ-009` and the final closure decision. It does not repeat Phase 006 by accepting historical results at face value. It validates the Phase 006 completion packet, freezes the exact product inputs and artifact, replays documentation-facing operator procedures, rejects stale or lower-fidelity evidence, and runs the final cross-matrix audit.

The master plan owns product scope, locked decisions, phase topology, the disallowed-defect boundary, and the exact completion endpoint. This file owns only the dependency-ordered execution of `SEFAUD-PHASE-007`. It may correct ordinary documentation, generated references through their owning generators, evidence indexes, and maintained documentation or evidence validators. It may not add product behavior, change the protected plan set or saved goal, weaken an earlier gate, publish a release, deploy to production, use credentials, or silently repair a product defect that belongs to an earlier phase. A newly discovered product, build, security, command, UI, persistence, integration, compatibility, or Phase 006 verification defect reopens its canonical owner and invalidates closure.

Phase 007 distinguishes three immutable identities:

1. The **Phase 006 verified product revision** is the integrated commit and signed Phase 006 tag whose complete clean-checkout matrix passed.
2. The **release artifact identity** is the exact `build/libs/sef-2.0.0.jar` content, SHA-256, SHA-512, packaged metadata, dependency manifest, and artifact-input digest verified by Phase 006. Documentation-only Phase 007 changes must not alter those inputs or bytes. If a rebuild is not byte-identical, closure stops until the cause is classified and all invalidated Phase 006 proof is rerun.
3. The **Phase 007 closure revision** is the integrated documentation and evidence commit. It must descend contiguously from the Phase 006 integration, contain no product or artifact-input change, describe only the frozen artifact, pass all documentation and final-audit gates, and receive the signed final phase tag after integration.

### Ordering, Failure Handling, and Safe Parallelism

- Task 001 is a hard gate. No documentation edit may begin while the Phase 006 merge, signed tag, complete matrix, artifact identity, evidence schema, ancestry, or workspace boundary is unresolved.
- Task 002 must complete before prose edits so current claims are not corrected by search-and-replace without evidence ownership.
- Task 003 may run concurrently with the read-only portion of Task 002 after identities are frozen. Generated files remain generator-owned; manual edits are prohibited.
- Tasks 004 and 005 may proceed in parallel by nonoverlapping paths after Tasks 002 and 003 define the final claims. One task owns a path at a time. Cross-links and duplicate authority are reconciled before Task 006.
- Task 006 is sequential by environment when fixtures share a server, client, provider, world, configuration, migration root, or evidence writer. Separate read-only link and claim checks may run concurrently.
- Tasks 007 and 008 may run in parallel only after the replay ledger is stable. Task 007 owns evidence contents; Task 008 owns validators. Neither may rewrite a failed result into success.
- Tasks 009 through 016 are sequential final gates. Any edit after Task 009 invalidates affected traceability and claim checks. Any edit after Task 012 invalidates the final clean verification and packet. Any post-merge repository-content change requires a new integration cycle before tagging.
- A documentation-only correction invalidates its claim row, links, terminology, generated-reference comparison where relevant, operator replay where it changes a step, final traceability, final audit, Definition of Done, diff audit, and packet. It does not automatically invalidate unrelated runtime proof when the evidence graph proves no behavioral or artifact-input intersection.
- A source, resource, build, dependency, schema, protocol, test-behavior, runtime-harness, generator-semantic, or artifact-input change invalidates the Phase 006 freeze. Stop Phase 007, route the change to its canonical earlier phase, integrate it sequentially, rerun Phase 006 completely after the last product change, and restart Task 001 from the new handoff.
- A required fixture or remote capability that is unavailable remains blocked. Do not replace it with prose, screenshots from another revision, mocks, headless startup, or static inspection.
- A failed command records exact expected versus actual behavior and a bounded sanitized decisive error. A successful retry receives a new attempt id, links the failed attempt, and states why the evidence became valid. Failure history is never erased.

## Architecture and Implementation Boundaries

### Documentation Ownership and Dependency Direction

Runtime registries, build metadata, schemas, code, tests, real workflows, and the final artifact are upstream authority. Generated references and ordinary documentation consume those facts. Documentation never becomes independent runtime authority. The final dependency direction is:

```text
integrated product and live contracts
  -> maintained tests and real workflows
  -> sanitized evidence and artifact identities
  -> generated references and ordinary documentation
  -> final traceability and release-readiness record
  -> post-merge wiki navigation
```

`README.md` remains the user entry point. `DOCUMENTATION.md` remains the maintainer and operator architecture reference. The tracked `docs` set owns focused installation, migration, compatibility, security, performance, feature, test, acceptance, release-note, and release-workflow detail according to the Phase 000 documentation inventory. Duplicate current authorities are prohibited. Historical audit and test documents may remain, but each historical section must retain its evidence revision and cannot override the final current ledger.

### Generated Content

`docs/COMMAND_REFERENCE.md`, `docs/PERMISSION_REFERENCE.md`, and `docs/CONFIGURATION_REFERENCE.md` are owned by `ProjectDocumentationGenerator` and `ModuleConfigRegistry`; `generateProjectReferences` is the only editing route. `docs/PERFORMANCE_REPORT.md` is owned by the performance report generator; `generatePerformanceReport` is the only editing route. Existing exact-drift tests remain mandatory. Phase 007 may improve validators or presentation only when the change does not alter live behavior or artifact inputs. A semantic generator change that changes represented contracts reopens the relevant upstream phase and Phase 006.

Generated references must distinguish executable action, discoverable schema, command fallback, and intentionally unavailable runtime. A schema or permission appearing in a generated file does not prove executable behavior. The sixteen families in `DEC-002` must be labeled consistently across diagnostics, UI, generated references, README, technical documentation, acceptance, and release notes.

### Evidence Model and Privacy

The Phase 000 evidence schema, stable ids, sanitization rules, invalidation graph, and approved restricted external root remain authoritative. Do not invent a second evidence directory or schema. The final tracked manifest is a bounded sanitized index. Raw logs, screenshots, recordings, profiles, dependency reports, corrupted fixtures, migration snapshots, world snapshots, and full runtime traces remain outside tracked source under restricted access.

Each final evidence record must include stable row id, requirement id, phase id, task id, test or workflow id, evidence class, required fidelity, result, expected result, actual result, product commit, closure commit where applicable, artifact SHA-256 and SHA-512 where applicable, environment id, fixture id, start and finish time, command or procedure id, bounded sanitized diagnostic, raw-evidence relative id and digest, invalidation inputs, prior attempt link, and reviewer disposition. It must not include credential values, userinfo-bearing URLs, real player identities, private messages, addresses, production paths, host home paths, production world data, or unbounded output.

If unsafe evidence is detected, stop propagation, quarantine it in the approved restricted root, record only the exposure class and affected evidence ids, invalidate every packet containing it, and request owner-led credential rotation if a real secret may have been exposed. Recreate proof with synthetic data. Do not store the secret or raw unsafe text in the remediation record.

### Configuration, Permissions, and Public Identifiers

Documentation must preserve exact configuration keys, permission ids, command routes, action ids, resource locations, schema versions, serialized fields, network versions, and optional-integration identities from the frozen product. Never normalize or rename literals for prose style. Every permission example must state its exact effect, default, actor/source scope, target scope, hierarchy or exemption rule, and dangerous wildcard implications where applicable. Generated references remain the exhaustive literal source.

Migration and rollback documentation must use actual current paths and commands from the frozen implementation and earlier persistence evidence. Unsupported newer data, corrupt data, source-fingerprint mismatch, backup conflict, stale revision, path safety failure, and partial publication must retain explicit fail-closed behavior. No point of no return is authorized. The prior approved JAR and exact compatible data snapshot remain rollback material through completion.

### Client, Provider, and Logical-Side Boundaries

Documentation must distinguish server-only mode, enhanced GUI disabled, matching enhanced client, no-SEF fallback client, incompatible enhanced protocol client, mixed clients, reconnect, and server switch. The universal JAR does not make client installation mandatory. The logical server owns permissions, policy, target selection, mutations, sessions, and durable state; clients own presentation only.

Optional providers remain optional and runtime guarded. LuckPerms API 5.4, FTB Essentials, Curios, and every advertised adapter must be described only to the exact present, absent, outage, refresh, removal, malformed, and fallback extent proven in the final matrix. Provider failure never grants authority. A blocked real-provider row blocks the corresponding compatibility claim and release readiness rather than becoming a generic limitation after the fact.

### Performance and Reproducibility

Documentation generation and validation must remain bounded and deterministic. It must not start a Gradle or game process per claim, scan outside the repository and approved evidence roots, perform unbounded network calls, or retain entire logs in memory. Parse each tracked document once, index anchors and stable ids once, and compare normalized exact sets. Record generation duration, input count, output count, and peak-size class. Two clean runs with shuffled discovery order and normalized environment paths must produce identical output digests.

Final artifact comparison uses exact bytes, entry inventory, metadata, dependency manifest, source and artifact-input digests, SHA-256, and SHA-512. A matching filename or version is insufficient. Documentation-only changes must not alter `build/libs/sef-2.0.0.jar`; if tool timestamps or nondeterministic packaging prevent byte identity, that is a reproducibility defect and Phase 006 remains open until resolved and rerun.

### Release Boundary and Rollback

This phase records release readiness only. It creates no release upload, GitHub release, platform draft, marketplace preview, deployment, credential, production change, or public publication. A later release task must obtain the owner's explicit authority, freshly verify platform mappings and artifact hashes, and use the then-current release workflow.

Before Phase 007 merge, rollback means removing only Phase 007-owned documentation, evidence-summary, and validator changes from its branch. After merge, rollback uses the signed Phase 006 integrated state for the previous product-and-doc baseline and the Phase 007 merge commit for the closure comparison. Product data is not migrated in this phase. The prior approved JAR and exact compatible data snapshot remain retained as documented rollback material. A Phase 007 rollback cannot make an unsafe or stale earlier artifact release ready; it merely restores the prior documented state.
