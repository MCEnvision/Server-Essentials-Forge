## Purpose and Ownership

This phase creates the reproducible baseline that every later audit and remediation phase consumes. It freezes the SEF 2 candidate lineage, preserves unrelated user state, derives authoritative inventories from source and live runtime contracts, reconciles those inventories with generated references and historical claims, and installs deterministic ownership and drift gates. Its canonical requirement is `SEFAUD-REQ-001`.

The master plan owns product scope, owner decisions, phase topology, the unavailable-control boundary, compatibility pins, and the plan-wide completion endpoint. This file owns only the detailed execution of `SEFAUD-PHASE-000`. It does not authorize a security repair, dependency change, command behavior change, UI polish, persistence repair, integration repair, release, or deployment. A product defect discovered while inventorying is assigned a stable finding and routed to its canonical later phase. A defect in the Phase 000 inventory, generator, reconciliation, evidence, or ownership machinery remains owned here and blocks this phase.

The phase distinguishes two revisions:

1. The **execution-base revision** is the integrated, approved candidate revision captured before Phase 000 work. It is immutable comparison evidence and must descend from `0c75bf25c58622096dfa7cc65a5f4b32e6d60ac4` without importing the legacy `forge-1.20.1` line.
2. The **frozen audit-baseline revision** is the merged and signed Phase 000 result after the last inventory, generator, test, or documentation correction. All downstream matrices bind to this revision. Any Phase 000 change before integration requires complete regeneration. Any later addition, removal, or identity-changing alteration of an inventoried surface trips drift gates and reopens the affected baseline gate.

### Ordering, Failure Handling, and Safe Parallelism

- Task 001 is a hard gate. If the plan set is still untracked, the candidate target is ambiguous, ancestry conflicts with `DEC-006`, signing fails, or tracked user changes overlap, stop without branch mutation.
- Task 002 is a hard gate for all captured evidence. Raw evidence created before the schema and sanitization rules pass cannot close a row.
- Tasks 003 through 008 may run concurrently using read-only discovery and isolated outputs. They must not choose competing owners; Task 009 resolves only from repository evidence and master ownership, never by arbitrary list order.
- Runtime commands that may write `run`, build caches, generated references, or temporary worlds use a clean disposable worktree or isolated configured game directories. Cleanup may remove only task-created paths whose exact identities were recorded. Unrelated workspace state is never used as a cleanup target.
- A failed generator or runtime run leaves its evidence row failed and preserves decisive sanitized output. Retry receives a new attempt id. Successful retry does not erase the earlier failure or its invalidation explanation.
- Phase-owned corrections run on the Phase 000 branch and must be small enough to attribute. A discovered product defect receives a stable finding linked to its inventory row and canonical later phase; Phase 000 does not suppress it to make counts reconcile.
- Any correction after Task 011 invalidates all output whose source files, registry, schema, build input, generated reference, or harness intersects the change. Task 012 reruns those rows and the full cross-inventory reconciliation. The final generation always occurs after the last change.

## Architecture and Implementation Boundaries

### Inventory Authority and Dependency Direction

Authority flows from the frozen source and runtime contracts to the inventories, then to generated references and documentation. Documentation, historical counts, tests that merely declare expectations, and recovery artifacts cannot create a product surface. The following source/runtime pairs must be joined rather than counted independently:

- `KernelServices`, `CommandCatalog`, `ShortcutRegistry`, `CommandDefinition`, command registrars, and the live Brigadier dispatcher define command identity. A registered parse node without a catalog owner and a catalog action without an executable or explicit negative contract are both discrepancies.
- `PermissionManifest`, `PermissionsHandler`, `PermissionDefinitionRegistry`, provider resolution, command requirements, GUI projection, and generated permission references define permission identity. Provider-derived dynamic permissions are inventoried separately from statically declared nodes.
- `PanelContracts`, `UniversalGuiCatalog`, `SefGuiServer`, session and payload records, client screens and menus, HUD contracts, command fallbacks, feedback emitters, and translations define UI identity. Client presentation never becomes authority.
- `StorageRepository` implementations, `KernelServices` registrations, `StorageCoordinator` diagnostics, documented paths, file API users, configuration owners, player-data adapters, and runtime writers define durable ownership. Interface implementation count and registered runtime count are distinct measures.
- Lifecycle event subscribers, explicit service start/stop methods, worker ownership, configuration revisions, provider refresh, session cleanup, and persistent flush paths define lifecycle ownership. An event annotation alone does not prove cleanup or ordering.
- Build declarations, resolved configurations, source sets, generated metadata, resources, runtime optional-mod guards, packaged entries, CI, and remote alerts define dependency and artifact-input identity. Phase 000 captures them but does not decide vulnerability applicability.

### Stable Identity and Row Schema

Each row id is derived from a semantic key such as canonical action id, normalized literal route plus executable owner, permission node, Java type plus UI role, durable owner plus normalized owned-root class, lifecycle event plus state owner, integration id plus adapter role, module id plus field id, dependency coordinates plus configuration, test unique id, documentation claim id, or artifact-relative path. Sort order and current count are not identity. Renames require an explicit predecessor/successor relation and invalidate dependent evidence.

Every row contains at least:

- row schema version, stable id, category, canonical owner, source locations, runtime identity where applicable, requirement and later phase;
- inputs, outputs, trust class, logical side, thread owner, authority source, permission and revision dependencies;
- durable or transient state touched, data classification, path class, schema and compatibility where applicable;
- normal behavior, failure behavior, recovery owner, performance or size bound, concurrency model, and unavailable/disabled semantics;
- required proof fidelity, fixture, exact evidence route, current evidence class and disposition, invalidated-by set, and linked findings;
- generation commit, environment id, normalized source digest, and deterministic ordering key.

The machine-readable representation must reject unknown required fields, duplicate semantic keys, duplicate stable ids, unknown owners, unknown phases, broken links, and a mandatory row without an evidence route. Human-readable summaries are derived views and cannot diverge from the machine-readable source.

### Command, Permission, Source, and Indirection Coverage

The command inventory must traverse canonical `/sef` routes and all other roots registered by `CommandRegistrationHandler` and domain registrars. It separately records executable leaves, grouping nodes, suggestions, aliases and shortcuts, catalog metadata, GUI actions, profiles, bundles, sudo, run and silent wrappers, panel actions, scheduled jobs, and server-control handlers. Each executable row joins canonical action id, feature, permissions, allowed source classes, target behavior, policy pipeline, cooldown identity, confirmation, domain owner, feedback, audit class, redaction class, persistence, and equivalent routes.

Source coverage cannot stop at `PLAYER`, `CONSOLE`, and `RCON` catalog defaults. It records command block, function, scheduled, GUI, alias, bundle, sudo, and server-profile execution where runtime code can create those contexts, including effective actor and origin. Unsupported contexts are explicit negative rows. The sixteen `DEC-002` families have schema and UI rows but negative runtime-handler and capability rows.

### UI and Feedback Coverage

Static discovery covers all client classes in `com.enviouse.sef.gui.client`, all `Screen` and container-screen subclasses elsewhere, menu classes, HUD registration and state contracts, pause-menu entry, Fancy Tags rendering/editor surfaces, InvSee, workstations, descriptor registries, workflow compilers, payloads, sessions, server projections, and command feedback. Each row records loading, empty, validation, failure, success, stale, disconnected, unavailable, and fallback ownership where applicable. Text feedback is product UI and joins its command action, component/translation source, audience, privacy class, and audit correlation.

### Persistence, Schema, Concurrency, and Recovery Coverage

Durable discovery begins with every `StorageRepository` implementation and runtime registration, then expands through all file, NBT, TOML, JSON, JSONL, archive, object, cache, project, journal, receipt, report, backup, export, marker, and player-data APIs. Known seed components include `AtomicFileStore`, `CoalescedPersistenceWorker`, player profiles, audit and optional file logs, module configuration, alternate accounts, Fancy Tags object and project stores, client caches, offline inventory NBT, economy import reports, exports, and migration journals. These seeds are not an exhaustive allowlist.

Each durable row declares normalized owned-root class without exposing a private host path, filename pattern, schema/envelope version, identity and cardinality, size/depth bounds, snapshot and write thread, synchronization and revision model, dirty/flush semantics, shutdown behavior, idempotency or outcome-unknown handling, corruption and unsupported-newer state, backup/quarantine/migration/rollback, retention, privacy, diagnostics, and tests. Cross-store references become explicit link rows. A volatile cache is a transient row unless its contents survive restart and affect later behavior; a disk cache is durable even when recreatable.

### Configuration, Lifecycle, Integration, and Compatibility Coverage

The configuration inventory begins at `ConfigHandler`, `ModuleConfigRegistry`, and `ModuleConfigService`, then joins every module, field, schema, apply class, dependency, conflict, secret class, revision, migration, backup, and generated-reference row. Bootstrap `common.toml` and modular TOML are distinct owners.

Lifecycle rows cover mod construction, manifest preparation, network registration, command registration, server starting/started, world and player load, tick, reload, module publication, provider refresh, logout, dimension change, stopping/stopped, worker timeout, and client disconnect. Each row records ordering, idempotency, logical side, thread, state created, state invalidated or settled, and failure behavior. Optional integration rows cover present, absent, configuration-disabled, startup-failed, runtime-failed, removed, and fallback states for every advertised adapter. Compatibility remains pinned by `DEC-004`; the inventory must detect but not perform a platform or protocol expansion.

### Security and Privacy of Evidence

Do not dump environment variables, credential stores, authentication tokens, full Git credential-bearing URLs, production logs, chat, IP addresses, UUIDs belonging to real users, home directories, or world data. Evidence uses synthetic actors and repository-relative paths. Remote URLs are normalized to remove userinfo. Command arguments and logs pass the same or stricter redaction than product output. Raw evidence uses restricted access in an approved external root; only bounded sanitized summaries may be tracked. If a secret is detected, quarantine the evidence, stop copying it, record only the exposure class, and request owner-led rotation outside this phase.

### Performance Boundaries

Inventory generation is bounded by repository and registry size and must not perform unbounded network calls, game ticks, entity scans, filesystem recursion outside declared project/evidence roots, or per-row Gradle/runtime startup. Derive registries once, normalize once, and join indexed maps by stable key. Record duration and peak-size metrics for generation. A new inventory gate must remain suitable for the maintained `check` or reference-generation lifecycle; expensive real-runtime reconciliation remains a separately named phase command with an explicit timeout.
